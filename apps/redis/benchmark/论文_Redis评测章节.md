# Redis 隔间隔离与软件加固性能评测

> 数据来源：`results.xlsx`（汇总自 r01–r07 共 7 组配置，SET/GET × value 大小 5/50/500，每组约 3 次重复取均值）。  
> 指标单位：请求吞吐量（requests/s）。评测方法对齐 FlexOS（ASPLOS'22）Redis 实验设定。

---

## 1. 实验目的

本节评估在 Unikraft 上基于 **Intel MPK 硬件隔间（compartment）** 与 **软件加固（software hardening / SFI）** 组合时，Redis 服务端吞吐相对单域基线的开销。关注两个正交维度：

1. **隔间数量与布局**：1 域（monolith）、2 域、3 域；
2. **软件加固覆盖面**：无加固、仅 Redis、多组件加固、全组件加固。

目标回答：隔间划分与加固是否会显著损害 Redis 吞吐；开销如何随请求 value 大小变化。

## 4. 结果分析

### 4.1 隔间数量的影响

对比 **r01（1 域，无加固）** 与 **r03（3 域，无加固）**，在 chunk=5 时：

- SET 下降约 **4.4%**，GET 下降约 **1.0%**；
- SET+GET 几何均值仅约 **−2.7%**。

在同为“仅 Redis 加固”的 **r05（2 域）** 与 **r04（3 域）** 之间，chunk=5 时 SET 变化约 +3.3%，GET 约 −13.0%。可见：从 1 域扩展到 3 域，小报文场景下开销总体落在个位数百分比量级，说明 **MPK 跨域切换代价在 Redis 热路径上可被接受**；3 域对 GET 略更敏感，可能与更多跨域调用落在读路径（协议解析 / 网络栈）有关。

### 4.2 软件加固的影响

在固定 2 域布局（redis+newlib \| uksched+lwip）下比较加固强度：

- r05（仅 redis）→ r06（redis+uksched+lwip）→ r07（全四组件）；
- chunk=5 时，相对 r05：r06 的 SET/GET 变化约 +1.0% / −1.3%，r07 约 +2.2% / +10.0%。

**未观察到“加固覆盖越广、吞吐单调下降”的规律。** 在本实验矩阵中，软件加固带来的额外开销被噪声淹没，甚至出现略高于基线的均值（如 r07 GET@5）。这表明：在当前实现与负载下，**加固更适合作为安全增强 knobs，而非吞吐的主要瓶颈**；吞吐主要由隔间边界位置与报文大小主导。

3 域下 r03（无加固）与 r04（仅 Redis 加固）在 chunk=5 上 SET +7.6%、GET −6.9%，同样落在测量波动范围内，支持上述判断。

### 4.3 Value 大小敏感性

所有配置均随 chunk 增大而吞吐下降，符合 Redis 与网络栈的拷贝/带宽特征：

- 相对 chunk=5，chunk=50 时 SET 约下降 15%–29%，GET 变化约 −22%–+5%；
- chunk=500 时 SET 约下降 59%–77%，GET 约下降 77%–88%。

小报文更能暴露隔间切换与加固检查的固定开销；大报文下这些固定开销被数据面成本稀释。因此论文讨论隔离开销时，**应以 chunk=5（及必要时 chunk=50）为主结论**，chunk=500 作为数据面主导场景的补充。

### 4.4 最优配置与安全–性能权衡

- **小 GET 最优**：r07（2 域全加固），约 919k req/s，相对 r01 +16.6%。
- **小 SET / 大 SET 最优**：r04（3 域 + Redis 加固），分别约 1018k / 349k req/s。
- **综合（chunk=5 几何均值）**：r05、r06、r07 均不低于基线；r03、r04 相对基线约 −2.6%–−2.7%。

实践含义：若安全策略要求将调度器与 TCP/IP 栈与应用分域，并启用应用侧加固，**r05/r07 类 2 域方案在 Redis 吞吐上可接近甚至略优于 monolith 基线**；进一步拆到 3 域（独立 lwip）时，小 GET 可能付出约一成量级代价，但仍属可讨论的工程权衡，而非数量级损失。

### 4.5 方差、可重复性与数据可靠性说明

1. **r01@chunk=500**：SET/GET 的变异系数（CV）分别约 **75% / 69%**，显著高于其它配置（多数 <15%）。该点导致大报文下 r01 显得“最差”，解读时必须注明不稳定性，建议复测或增加迭代后再写入最终结论。
2. **r02 与 r07 配置相同**，但 chunk=5 SET 相差约 **+28%**（786k vs 1007k），GET 相差约 +4%。说明单次 3 轮均值仍可能受 QEMU/调度/缓存热身影响。论文中建议：
   - 将 r07 作为该配置的代表，或对等价配置取合并均值；
   - 报告误差棒（min–max 或标准差），避免仅报点估计；
   - 对关键结论增加迭代次数（例如 ≥5）。
3. **r04@chunk=50 GET** 的 CV 约 33%（单次异常低值 431k），拉低均值，比较 2D/3D GET 时宜同时给出中位数或剔除离群点的敏感性分析。

## 5. 小结（可直接写入论文结论段）

本文在 Unikraft + MPK 上对 Redis 进行了 7 组隔间布局与软件加固组合评测。主要结论如下：

1. **小报文（5 字节）场景下，1 域到 3 域扩展的吞吐损失约 3% 量级（几何均值 −2.7%），未出现数量级退化。**
2. **软件加固覆盖从“仅应用”扩展到“全组件”时，吞吐未呈现系统性恶化**；在 2 域布局下，全加固配置（r07）的小 GET 甚至取得矩阵最优。
3. **报文增大后，吞吐下降主要由数据面主导**；隔离相关固定开销被稀释。大报文下基线方差偏大，相关对比需谨慎报告。
4. **安全增强的 2 域方案（如 r05/r07）在 Redis 上可实现接近 monolith 的吞吐**，表明 MPK 隔间 + 选择性加固适合作为 Redis 类网络服务的实用加固路径。
